## Shake to Trick (#430)

Android gains an off-by-default **Controls → Shake to Trick…** setting. iPhone
and iPad expose their existing setting at the same level, separate from
**Motion Steering…**. Both use gravity-free acceleration, a settling threshold,
a trigger threshold and a cooldown. A connected physical controller takes
priority. Existing Apple preferences are retained. Mac/tvOS do not expose a
handset motion control.

The Apple motion callback previously returned immediately when a flat device
had too little gravity in the screen plane to calculate a steering angle.
That also skipped shake detection. The candidate now outputs neutral steering
in that orientation and still evaluates the shake.

Validation:

- Source review covered default/persistence, independent tilt and shake
  registration, controller priority, pause/focus cancellation and input release.
- Python suite: **344 passed, 1 skipped, 214 subtests passed**. After making the
  JVM test find its JDK/cache portably, the gesture and iOS menu subset passed
  again (7 tests).
- Production Kotlin detector and sensor class executed on the JVM: settling,
  cooldown, a sustained impulse, flat z-axis input, tilt independence, absent
  sensors, disable, resume and ignored callbacks after stop.
- Native `kartpad_mobile_motion_steering_tests` build and CTest passed, including
  the requirement to settle before the first gesture.
- Android `:app:assembleDebug` fixture built. On a dedicated API 36 emulator,
  `scripts/test-android-shake-tricks.py emulator-5580` navigated the actual UI,
  checked saved on/off state through relaunch, injected accelerometer events,
  observed D-pad Up press (`buttons=1`) and release (`buttons=0`), and verified
  suppression while the menu was open and while disabled.
- iOS arm64 device-target app built from the pinned runtime and clean pinned
  DiscIO dependency. Repository IPA/app-content audit and matching dSYM UUID
  check passed. This app contains no game code and was not installed on a phone.

These checks do not prove comfortable physical shake sensitivity or successful
in-race tricks/wheelies. Before release, check a physical Android phone and
an iPhone/iPad: flat and tilted gestures, normal handling without accidental
tricks, a jump and bike wheelie, controller takeover, menu/background/resume,
and persistence. Verify the Apple sheet on both phone and tablet. No physical
app was replaced during this pass; player containers remain untouched.

The emulator script uses existing debug fixture entry points, requires an
explicit emulator serial and does not install or clear application data. It
changes that disposable fixture's setting and ends with shake disabled. The
JVM test requires the pinned Kotlin compiler cached by the Android Gradle build;
it skips explicitly when those local build dependencies are absent.

## Android graphics (#304, #104, #301, #431)

The latest [#304 attachment](https://github.com/user-attachments/files/33062073/KartPad-private-diagnostics.3.zip)
is version 0.7.14/build 258 on PowerVR BXM-8-256. Its useful comparison reports
149,544 covered pixels in all three copies. The alternate vertex layout differs
in all 149,544 pixels; the constant-index copy has zero differing pixels against
the original. Two earlier samples were pipeline-not-ready. The log ends after
backgrounding; historical process-exit records do not establish a crash in that
specific run.

This establishes disagreement between layouts, **not which output is right**.
Likewise, empty original/alternate/constant comparisons in the S24 Ultra #104
and most Moto G85 #301 captures cannot exclude vertex fetching or establish a
bone-indexing cause. One G85 sample drew only the original path. Previous
support conclusions were too strong; #304 received a correction in Spanish.

Reviewed the retained offscreen comparison, pipeline/uniform pairing and
shader/CPU vertex conversion paths. No bounded correction with a known-good
comparison emerged. Do not enable either experimental workaround by default.
The next discriminating step needs a representative failing draw and reference
output on the affected GPU, not another settings matrix sent to reporters.

HONOR #431–434 share the same report ID, device/build/settings and symptom.
All were assigned to Chris. #431 is canonical; #432–434 were closed as
duplicates. One concise Spanish request for a screenshot and the reviewed
standard diagnostic is on #431; there is no supplied capture to diagnose yet.

## Startup flicker (#390)

Reviewed the existing 20.24-second, 60 fps [screen recording](https://github.com/user-attachments/files/33007553/IMG_3969.zip)
and [diagnostic log](https://github.com/user-attachments/files/32999462/Latest-KartPad-Diagnostic.log).
Around 12–17 seconds, the game image and rendered FPS panel disappear while
native touch controls remain visible. The title screen is subsequently stable.
The FPS panel is drawn through ImGui into the presentation image, separately
from the game's image; this makes a game-only fade or skipped GX draw an
incomplete explanation. It does **not** identify a surface/compositor bug by
itself.

The 0.7.4/build 247 log uses Metal BGRA8Unorm with Immediate presentation.
Recorded slow jobs are primarily surface acquisition; rolling FPS is roughly
60. Those counts do not prove every displayed image is valid. The video and
log are separate captures and must not be treated as frame-synchronized.

Next bounded check: reproduce the startup on a 60 Hz iPhone, compare a captured
presentation image (including FPS) with the device recording at a blackout,
then investigate the side of that boundary that loses the image. Do not change
pacing or shader defaults merely because this is 60 Hz hardware. The attached
iPhone 14 requires its passcode; no physical reproduction was possible in this
pass. The reporter has already supplied enough to begin; no new log requested.
